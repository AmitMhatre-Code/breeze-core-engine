# Bug audit — 2026-09-28

A code-reading audit of the backend and the key frontend helpers, done after the stale-price bot incidents. Fixed findings are marked in the table and in their entry; everything else is still open. Each entry says what happens, where, and why it looks like a bug rather than a design choice. Everything was checked against `guide/technical/design-decisions.md` so deliberate behaviour (serialized broker calls, fail-closed licensing for *new* trades, advisory shedding, and so on) is not reported.

## How this was done

- Read the money paths end to end instead of relying on the tests: WebSocket feeds and tick pipeline, the quote router and chain builder, the P&L engine and Strategy Group (SG) dispatch/lifecycle, all five bots, the ICICI transport and pacer, licensing and heartbeat, reference data, and the frontend order and portfolio helpers.
- Four findings were reproduced with throwaway pytest probes (B-52 added on 2026-09-29) run against the real modules (in-memory Redis, temp SQLite). The probes are not in the repo; their output is in [Runtime probes](#runtime-probes).
- "Confidence" means: **Confirmed** = reproduced at runtime; **High** = follows directly from the code; **Medium** = depends on broker or deployment behaviour that could not be observed locally (there is no live ICICI access off the static IP), with the assumption stated.

## Severity

- **Critical** — can open an unintended position (including a naked short) without the user acting.
- **High** — can leave a position unprotected, or drive trades and stops off wrong prices, in plausible conditions.
- **Medium** — degrades protection, sizing or data correctness in specific but realistic conditions.
- **Low** — edge cases, bookkeeping, noise, or hardening.

### B-01 · Iron Fly and CAS Bingo re-send closing orders for legs already closed or never filled

**Where:** [iron_fly_bot.py:1039 `_close_live`](../backend/src/icici_breeze_backend/app/services/bots/scalping/iron_fly_bot.py#L1039), [iron_fly_bot.py:907 `_abort_live_entry`](../backend/src/icici_breeze_backend/app/services/bots/scalping/iron_fly_bot.py#L907), [cas_bingo/execution.py:462 `close_live`](../backend/src/icici_breeze_backend/app/services/bots/cas_bingo/execution.py#L462), [cas_bingo/execution.py:352 `_abort_live_entry`](../backend/src/icici_breeze_backend/app/services/bots/cas_bingo/execution.py#L352), [scalping/runtime.py:760 `_exit_only_bots`](../backend/src/icici_breeze_backend/app/services/bots/scalping/runtime.py#L760)

**What happens:**
- When `_close_live` cannot close every leg, it writes `detail["exit_partial"] = {closed, stuck}` and leaves the cycle open. It never removes the closed legs from `cycle.legs`.
- When an entry fails and the unwind leaves anything "stuck", `_abort_live_entry` leaves the cycle open with `legs=plan.as_legs()`: every *planned* leg at the full planned quantity, including legs that never filled.
- The bot is disarmed, but `_exit_only_bots` keeps ticking any bot with an open live cycle. The next exit verdict re-runs `_close_live` over `cycle.legs`. Hard square-off, window end, drift, stop or stale feed all produce one.
- That buys back shorts that were already bought back, which opens new longs. It sells wings that were already sold or never bought, which opens **new naked shorts**.
- CAS Bingo behaves the same way for `exit_partial` cycles, because they carry `net_entry_per_unit`, so `evaluate_exit` still produces a verdict. At expiry, `settle()` also books P&L over every leg in the cycle, including legs never held or already closed.

**Why it is a bug:** The comments say the open row is kept "so the exit loop keeps trying to manage it". But the data the loop manages is the *intended* structure, not what is actually held. Nothing reconciles `cycle.legs` with what filled or closed.

**Trigger:** Any exit or unwind where one leg is rejected, throttled past its attempts, or not filled at the ladder's price. These are plausible in fast markets and on thin wings.

**Fixed 2026-09-29** ([design-decisions #53](../guide/technical/design-decisions.md#53-a-live-multi-leg-cycles-legs-are-what-it-holds-now-and-a-close-that-sticks-is-retried-only-against-the-brokers-positions)). `scalping/held_legs.py` rewrites `cycle.legs` to what is still held after every close and unwind, and uses `filled_quantity` so partial fills count. It never sells a long while its short is open, and books P&L leg by leg. Each retry is checked against the broker's positions and bounded. Rows stuck by the old code are rebuilt at startup. Two defects found in the same code are fixed with it: partly filled closes were recorded at full size, and wings were sold while their short was stuck. Tests: `test_scalping_iron_fly_live.py` and `test_cas_bingo.py` (the B-01 sections).

### B-02 · A crash mid-entry leaves a "pending" cycle that the exit path later trades as if it were filled

**Where:** [momentum_bot.py:741](../backend/src/icici_breeze_backend/app/services/bots/scalping/momentum_bot.py#L741), [iron_fly_bot.py:846](../backend/src/icici_breeze_backend/app/services/bots/scalping/iron_fly_bot.py#L846), [cas_bingo/execution.py:275](../backend/src/icici_breeze_backend/app/services/bots/cas_bingo/execution.py#L275), [guards.py:194 `reconcile_pending_cycles`](../backend/src/icici_breeze_backend/app/services/bots/scalping/guards.py#L194), [guards.py:308 `has_unresolved_intent`](../backend/src/icici_breeze_backend/app/services/bots/scalping/guards.py#L308)

**What happens:**
- Live entries write the cycle first with `detail.pending=True, order_ids=[]`. Order ids are only recorded in `mark_cycle_placed` *after* `place_and_confirm` returns, which includes the fill wait and any cancel.
- If the process dies in that window, the row has no order ids. The deployment has documented OOM kills (#41) and portal recreates. A DB exception in the same window has the same effect.
- At startup `reconcile_pending_cycles` can only send an orphan alert. The row stays pending and is re-alerted on every restart. `has_unresolved_intent` then blocks entries **permanently**; there is no date filter, although the docstring says "for the session".
- Worse, a pending row is an open cycle, so the scalper snapshot reports `has_open_position=True` and `inspect_position` manages it. At hard square-off, stale feed or window end, `_close_live` trades the **planned** legs with `paper=False`.
  - The Long Scalper sells the planned quantity. If the buy never filled, that is a naked short.
  - The Iron Fly buys back two shorts and sells two wings that may never have been bought.

**Why it is a bug:** The design (#32/#43 style "row before order") exists so a crash leaves "a question startup can answer". Because the ids are written late, the question can never be answered. Also, CAS Bingo's exit loop skips pending rows ([cas_bingo/runtime.py:313](../backend/src/icici_breeze_backend/app/services/bots/cas_bingo/runtime.py#L313)) but the scalpers' does not.

### B-03 · An SG's own exit fill is treated as manual intervention while its other legs are still being placed

**Where:** [squareoff_dispatcher.py:298 `_handle_group_rule_hit`](../backend/src/icici_breeze_backend/app/services/squareoff_dispatcher.py#L298), [strategy_group_lifecycle.py:159](../backend/src/icici_breeze_backend/app/services/strategy_group_lifecycle.py#L159), [strategy_group_lifecycle.py:308 `_handle_foreign_order`](../backend/src/icici_breeze_backend/app/services/strategy_group_lifecycle.py#L308), [squareoff_rules.py:377 `mark_fired`](../backend/src/icici_breeze_backend/app/repositories/squareoff_rules.py#L377)

**What happens:**
1. The dispatcher marks the rule `triggered`, then places legs one at a time. Placement is serialized and freeze-sliced, so this takes seconds.
2. The order ids are only persisted at the end, by `mark_fired` or `mark_fire_failed`.
3. Meanwhile the order feed delivers the first leg's fill. `on_order_notification` finds the `triggered` rule, whose `leg_results` is still `NULL`, so `order_ids_for_rule(rule)` is empty.
4. The fill is therefore classed as foreign and the rule is **Reset** with "you traded NIFTY 26000 CE outside this rule". That also releases the WS pin and sends a Reset Telegram alert.
5. Any later chunk that hits a throttle checks `_still_firing`, sees `reset`, and **stops retrying**. The position is left half-closed.
6. `mark_fired` and `mark_fire_failed` have no status guard, so they overwrite the Reset afterwards.

**Why it is a bug:** Order identity is the lifecycle's discriminator ("our exit vs the user's trade"), but the identity isn't known to the lifecycle until after the fills it is supposed to classify. Only the reconcile path is tested for `triggered` (`test_triggered_rule_is_not_reset`), not the notification path. Reproduced; see [probe 1](#runtime-probes).

**Note:** [B-19](#b-19) may currently *mask* this for the production user, because the lookup by `n.user_id` may miss. Fixing B-19 alone would expose B-03.

### B-04 · The chain builder serves ticks up to ~4 minutes old as fresh `websocket` quotes

**Where:** [chain_build_service.py:36 `_read_raw_tick`](../backend/src/icici_breeze_backend/app/services/chain_build_service.py#L36), [chain_build_service.py:63 `_normalize_and_cache_cell`](../backend/src/icici_breeze_backend/app/services/chain_build_service.py#L63), [ws_tick_normalize.py:171](../backend/src/icici_breeze_backend/app/services/ws_tick_normalize.py#L171), [quote_source_router.py:1325 `row_is_live`](../backend/src/icici_breeze_backend/app/services/quote_source_router.py#L1325)

**What happens:**
- Every rebuild re-reads each contract's raw tick. The chain-builder rebuilds every ~2 s, and request paths such as `wait_for_strike_quote` rebuild on every poll.
- The raw key has a 120 s TTL (`WS_RAW_QUOTE_TTL_SECONDS`, which defaults to 120 in `core/config.py`, not the 300 the architecture doc states).
- `_read_raw_tick` throws away the stored `received_at`. `normalize_icici_tick(raw)` is called without `updated_at`, so the cell is stamped `time.time()` and re-written to `ws_quote_key` with a fresh 120 s TTL.
- So a contract that stopped ticking keeps appearing as a just-updated `websocket` cell for up to ~120 s. The cell then survives up to another ~120 s.
- `row_is_live()` and the scalpers' `Quote.live` check only `quote_source == "websocket"`, never the age.

**Consequences:**
- Bots enter, mark, trail and stop on minutes-old prices, with a feed that looks healthy.
- Order pricing is affected too: `wait_for_strike_quote` says it rebuilds "so an aggressive limit order is not priced off a two-second-old book", but the rebuild just re-stamps the same old tick.
- The Portfolio LTP override in `get_positions` prefers the websocket cell over the broker's own LTP.
- The UI's "Live · WebSocket" badge and `quote_as_of` are fooled as well.

This is the most direct remaining cause of "bots working off stale prices". Reproduced; see [probe 2](#runtime-probes).

<a id="b-05"></a>
### B-05 · One Redis error kills the tick-cache thread for the life of the process

**Where:** [ws_tick_pipeline.py:379 `_cache_loop`](../backend/src/icici_breeze_backend/app/services/ws_tick_pipeline.py#L379), [ws_tick_pipeline.py:394](../backend/src/icici_breeze_backend/app/services/ws_tick_pipeline.py#L394)

**What happens:**
- `_cache_loop` has no `try/except` around `cache_set_json`. The Redis client uses `socket_timeout=2`, so one timeout is enough to raise; so is a connection reset while the `breeze-redis` sidecar is recreated, or a BGSAVE fork stall on a small instance.
- The exception ends the `ws-tick-cache` thread. `_started` stays `True`, so neither `start_tick_pipeline()` nor `reconnect_ws()` ever restarts it.
- From then on, raw ticks stop reaching Redis. The chain builder has nothing new; websocket cells expire; chains fall back to snapshot, bhavcopy or REST stand-ins; bots pause; and the quote snapshot stops capturing.
- The price watchdog reads the same raw keys, so it sees silence. It re-subscribes successfully (the socket is fine), so per [B-17](#b-17) it never escalates. Nothing recovers until the process restarts.
- The P&L engine is unaffected, because its flush loop has its own error handling.

Reproduced; see [probe 3](#runtime-probes).

<a id="b-06"></a>
### B-06 · A failed Portfolio/Dashboard positions fetch wipes the P&L engine's legs, disarming SG evaluation

**Where:** [route_portfolio.py:159](../backend/src/icici_breeze_backend/app/api/v1/route_portfolio.py#L159), [dashboard_bootstrap.py:161](../backend/src/icici_breeze_backend/app/services/dashboard_bootstrap.py#L161), [portfolio_pnl_engine.py:175 `sync_positions_from_response`](../backend/src/icici_breeze_backend/app/services/portfolio_pnl_engine.py#L175)

**What happens:**
- Both routes pass *any* dict from `get_positions` to `sync_positions_from_response`, including `{"Status": 400/429, "Success": None}`. `get_positions` returns that for no session, SDK exceptions, ICICI throttles and the daily cap.
- For a non-list response, `sync_positions_from_response` calls `clear_positions(user_id)`. `run_pnl_tick` then skips the user entirely, so no armed SG is evaluated.
- With the Portfolio page open (it polls), every failing poll wipes the registry. Only the protection guard (every 60 s) or a later successful poll refills it.

**Why it is a bug:** `squareoff_protection_guard.warm_positions_for_user` documents exactly this hazard: "Handing it a failed fetch would therefore *wipe* a registry that was already warm". It checks `Status == 200` first. The other two writers do not. The effect is worst during ICICI trouble, which is exactly when stops matter.

### B-07 · ICICI REST calls have no timeout while the per-user broker lock is held

**Where:** breeze_connect `make_request` (installed SDK, `breeze_connect.py` ~L1139), [requests_patch.py:216](../backend/src/icici_breeze_backend/app/core/requests_patch.py#L216), [requests_patch.py:248](../backend/src/icici_breeze_backend/app/core/requests_patch.py#L248), [icici_api_pacing.py:402](../backend/src/icici_breeze_backend/app/services/icici_api_pacing.py#L402)

**What happens:**
- The SDK calls `requests.get/post/put/delete` with no timeout. The patch forwards `timeout=kwargs.get("timeout")`, which is `None`. `GlobalIciciApiLimiter` holds the per-user `threading.Lock` for the whole call.
- One stalled read (a gateway hang or a black-holed connection) blocks **every** subsequent broker call for that user until the OS gives up, which can be many minutes. That includes SG stop-loss exits, bot exits, cancels and the protection guard's position warm.

**Why it is a bug:** Design #24 serializes calls deliberately, but serialization makes a missing timeout a whole-account freeze rather than one slow call. `reap_stale_runs` even documents "a blocked broker call with no timeout". The `core/icici_client` "timeouts" wrapper is not on this path.

### B-08 · `async def` routes run blocking broker work on the event loop that also runs PB/SL

**Where:** e.g. [route_portfolio.py:148 `/portfolio/data`](../backend/src/icici_breeze_backend/app/api/v1/route_portfolio.py#L148), [home.py:578 `/home/data`](../backend/src/icici_breeze_backend/app/api/v1/home.py#L578), [home.py:190 `/updatemaster`](../backend/src/icici_breeze_backend/app/api/v1/home.py#L190), and most of `route_book`, `route_order`, `route_bots`, `route_dashboard` and `route_settings`. About 200 `async def` handlers exist, and almost none use `to_thread`.

**What happens:**
- FastAPI runs `async def` handlers on the event loop. These handlers call synchronous broker code directly.
- `get_positions` does REST calls, `margin_calculator`, per-leg router lookups and chain waits, and the pacer can sleep up to 20 s for a minute slot. `/updatemaster` downloads and rebuilds the ICICI master. `break_order` places many chunks.
- There is one uvicorn process. The P&L rule loop (`run_pnl_loop`), the P&L quote flush, the feed watchdogs, the index-signal publisher and the heartbeat are all asyncio tasks on that same loop.

**Why it is a bug:** Stop-loss evaluation latency now depends on unrelated HTTP traffic. A slow Portfolio poll or a master refresh stalls rule evaluation and tick flushing for its whole duration. It also makes [B-09](#b-09)'s staleness window and [B-16](#b-16) worse.

<a id="b-09"></a>
### B-09 · Licence read-only mode blocks stop-loss exits and other risk-reducing actions

**Where:** [squareoff_dispatcher.py:311](../backend/src/icici_breeze_backend/app/services/squareoff_dispatcher.py#L311), `require_trading_not_revoked` on `/book/cancel-one`, `/book/cancel-commit`, `DELETE /squareoff-rules/{id}`, `POST /squareoff-rules/{id}/cancel-orphan-orders`, `DELETE /gtt-exit-orders/{id}`, `PATCH /bots/config` and parked-order deletes. Also [deployment_license_status.py:59](../backend/src/icici_breeze_backend/app/services/deployment_license_status.py#L59) and [portal_deployment_heartbeat.py:333](../backend/src/icici_breeze_backend/app/services/portal_deployment_heartbeat.py#L333).

**What happens:**
- When the licence reads as read-only, a breached SG is marked fire-failed and **no exit orders are sent**. The user also cannot cancel orders (including orphans that would *open* a contra position), disarm an SG, cancel a GTT, or switch a bot off.
- Read-only is not only a revoked licence. It is also "no verified heartbeat for 2× the interval", and "no heartbeat verified yet" at startup.
- The heartbeat loop waits a full interval after a failure. The staleness boundary is exactly 2× the interval, so a *single* failed heartbeat lands the next attempt just past the boundary. That produces a short read-only window, longer if the loop is blocked ([B-08](#b-08)). Two failures give up to a full interval (5–60 min).

**Why it is a bug:** The code states the opposite principle elsewhere. `scalping/decide.py`, rule 1: "a gate that blocks *entering* must never block *leaving*… would strand a live position with no stop running the moment a licence lapsed." #16's fail-closed rationale is about not *enabling trading*; blocking exits and cancels increases risk instead.

<a id="b-10"></a>
### B-10 · CAS Bingo cancels SENSEX (BFO) orders on NFO, so they cannot be cancelled

**Where:** [scalping/live.py:219 `cancel`](../backend/src/icici_breeze_backend/app/services/bots/scalping/live.py#L219), [processor.py:1926](../backend/src/icici_breeze_backend/app/services/processor.py#L1926)

**What happens:**
- `place_and_confirm` places on the leg's exchange: BFO for SENSEX in CAS Bingo. On a timeout it calls `live.cancel(proc, user_id, order_id)`, which passes a bare order id.
- `cancel_order_single` defaults `exchange_code = NFO` unless the id carries `|EXCH`, so the cancel goes to the wrong exchange and fails.
- The bot sets `cancel_failed`, disarms and alerts "could not be cancelled", while the BFO order keeps resting and can fill into an unmanaged position.

**Why it is a bug:** `_rest_order_state` in the same file does pass `exchange_code`, and its docstring explains why ("an order looked up on the wrong exchange simply is not found"). `cancel` was missed.

<a id="b-11"></a>
### B-11 · Holdings Writer treats an unreadable positions call as "no calls written yet"

**Where:** [holdings_writer.py:253](../backend/src/icici_breeze_backend/app/services/bots/holdings_writer.py#L253) and [:807](../backend/src/icici_breeze_backend/app/services/bots/holdings_writer.py#L807), [proposals.py:148 `price_edited_leg`](../backend/src/icici_breeze_backend/app/services/bots/proposals.py#L148)

**What happens:**
- `_existing_short_lots(proc.get_positions(user_id), …)` is used without checking `Status`. A throttle, session or SDK failure returns `Success: None`, which is read as zero existing short calls.
- `covered = deliverable // lot − 0`, and the autonomous path (`fire_autonomous`) can then write calls on top of calls already written. That is uncovered call exposure.
- Existing shorts are also divided by the *target* expiry's lot size, so a lot-size revision miscounts them.
- Separately, the approval edit cap in `price_edited_leg` uses `held_quantity`, which includes pledged and blocked shares, instead of the scan's `deliverable_quantity`. And `price_contract` returns a leg even when its margin could not be priced, although its comment says such a leg is dropped.

**Why it is a bug:** The bot's premise is "calls are backed by stock"; the cap must fail closed. Failure to read positions currently fails open.

### B-34 · Customer instances serve the app, its cookies and logins over plain HTTP

### B-52 · Live scalper cycles never record `entry_value`, so the daily stop reads a live Iron Fly as a large loss

*Added 2026-09-29, found while fixing [B-01](#b-01).*

**Where:** [iron_fly_bot.py:852 `_open_live`](../backend/src/icici_breeze_backend/app/services/bots/scalping/iron_fly_bot.py#L852), [iron_fly_bot.py:1035 `_record_live_entry`](../backend/src/icici_breeze_backend/app/services/bots/scalping/iron_fly_bot.py#L1035), [momentum_bot.py:740](../backend/src/icici_breeze_backend/app/services/bots/scalping/momentum_bot.py#L740), [guards.py:123 `unrealized_pnl`](../backend/src/icici_breeze_backend/app/services/bots/scalping/guards.py#L123), [runtime.py:617 `_unrealized_from`](../backend/src/icici_breeze_backend/app/services/bots/scalping/runtime.py#L617), [decide.py:163 `_decide_exit`](../backend/src/icici_breeze_backend/app/services/bots/scalping/decide.py#L163)

**What happens:**
- A live cycle's row is written before any order, with `entry_value=None`. The fills are then recorded only in `detail`: `net_credit_per_unit` for the fly, `entry.price` for the Long Scalper. `mark_cycle_placed` rewrites `detail` and nothing else, so `entry_value` stays NULL for the life of the cycle.
- `guards.unrealized_pnl` reads `entry_value or 0`. For the fly it returns `0 − cost to close`, which is the whole buy-back cost as a loss. For the Long Scalper it returns `bid × qty − 0`, which is the whole position value as a gain.
- That figure is the unrealized half of the cumulative daily stop (`stop_breached`: realized + unrealized ≤ −`cumulative_stop_inr`). `_decide_exit` checks the stop straight after the hard square-off, ahead of the position's own target and stop.
- **Iron Fly:** almost any live fly breaches the cap on its first exit pass, because it only takes cost-to-close × quantity above the cap (default ₹10,000). The decision is `terminated_for_day`: the fly is bought back at once and the bot stands down for the day. Every live entry pays a full round trip of friction and never trades its plan. See [probe 4](#runtime-probes): a fly that is really +₹6,975 is marked at −₹34,200.
- **Long Scalper:** the open position counts as a gain equal to its full market value. A losing open trade therefore pushes the stop test *away* from the cap instead of towards it. A day already close to the cap is not stopped while that trade is open, and the trade's own ladder stop is the only thing left.
- The same wrong figure is written to the run's audit detail as `gates.unrealized_pnl`.
- Not affected: paper cycles, which set `entry_value` at open ([iron_fly_bot.py:688](../backend/src/icici_breeze_backend/app/services/bots/scalping/iron_fly_bot.py#L688), [momentum_bot.py:667](../backend/src/icici_breeze_backend/app/services/bots/scalping/momentum_bot.py#L667)), and CAS Bingo, which sets it after its fills (`execution._set_entry_value`) and does not use this stop.

**Why it is a bug:** `unrealized_pnl` documents `entry_value` as the credit received, and every paper path sets it. The live paths leave it empty and nothing fills it in afterwards, unlike CAS Bingo. So paper evidence cannot predict live behaviour. A fly that runs to its target on paper is stopped out as soon as it goes live, and the Long Scalper's daily cap is weaker live than on paper.

**Trigger:** Iron Fly: every live entry. Long Scalper: any live trade that is losing while the day's realized loss is near the cap.

<a id="b-40"></a>
### B-40 · The pacer's per-call spacing is skipped for calls queued on the lock

[icici_api_pacing.py:146 `wait_for_slot`](../backend/src/icici_breeze_backend/app/services/icici_api_pacing.py#L146): spacing is computed before the per-user lock is taken, so calls queued on the lock fire back-to-back when it frees. The configured spacing is not enforced under contention.

<a id="b-41"></a>
### B-41 · Single-contract quote lookups subscribe tokens that are never released

[quote_source_router.py:596 `_fetch_cell_from_cache`](../backend/src/icici_breeze_backend/app/services/quote_source_router.py#L596): each single-quote lookup subscribes its contract under `__untracked__`, which is never released. Subscriptions accumulate for the life of the process. If ICICI caps subscriptions per session, which is unverified, new chains would silently get no feed.

<a id="b-42"></a>
### B-42 · Iron Fly sizing falls back to the minimum instead of the largest verified size

[iron_fly_bot.py:246 `size_fly`](../backend/src/icici_breeze_backend/app/services/bots/scalping/iron_fly_bot.py#L246): if the estimate and one step down both exceed the ceiling (3-call cap), it returns `min_lots` rather than stepping further. For example, it can trade 1 lot when 9 would fit.

<a id="b-43"></a>
### B-43 · CAS Bingo settles a missed expiry at a later day's index level

[cas_bingo/runtime.py:305](../backend/src/icici_breeze_backend/app/services/bots/cas_bingo/runtime.py#L305), [cas_bingo/market.py:86](../backend/src/icici_breeze_backend/app/services/bots/cas_bingo/market.py#L86): an expired cycle is settled at `last_index_level()`, the latest cached level with no date check. ### B-44 · Exit ladders price a missing quote at ₹0.05

[iron_fly_bot.py:1079](../backend/src/icici_breeze_backend/app/services/bots/scalping/iron_fly_bot.py#L1079) (`_close_live`) and [cas_bingo/execution.py:416](../backend/src/icici_breeze_backend/app/services/bots/cas_bingo/execution.py#L416) (`_close_leg`) use `quote.ask or 0.05` / `quote.bid or 0.05`. ## Needs a live check before acting

## Checked and not reported

- Serialized broker calls, advisory shedding, the reserved order budget and fail-closed licensing for *new* trades are intentional (#16, #24).
- Bot 2 cannot double-fire after a crash: reaped runs are coded `interrupted`, which the day gate counts as done.
- `/order` idempotency keys hold in practice, because the handler runs serially on the event loop. They would stop holding if the route were moved to a thread without adding a lock.
- Calendar helpers receive timezone-aware datetimes at every call site checked.
- The in-memory Redis `expire()` does not apply to string keys, but no current caller relies on it.
