# Options Strategy Engine Specification

## 1) Goal

Build a simple options strategy engine that:

1. Uses `scrip_master` to enumerate all tradable strikes for a given **scrip + expiry**.
2. Uses `get_option_chain_quotes` to enrich strikes with market liquidity and quote data.
3. Filters to a **liquid universe** where:
   - `Total Buy Qty > 0`
   - `Total Sell Qty > 0`
4. Generates and ranks strategies across three families:
   - **Income**
   - **Directional**
   - **Volatility**
5. Asks the user only for:
   - **Target PoP**
   - **Margin to deploy**
   - **Max Loss appetite**
   - Optional **range outlook** only when required
6. Sizes each strategy using both:
   - **Margin constraint**
   - **Max loss constraint**
   - Optional **ELM provisioning** if the user wants it

The output should be a short list of the best strategy candidates with their legs, quantities, expected credit/debit, margin requirement, max loss, breakevens, and selection score.

---

## 2) Core API Inputs and Assumptions

### 2.1 Available data sources

#### `scrip_master`
Provides the full set of strikes for a selected `scrip + expiry`.

#### `get_option_chain_quotes`
Can be called in two modes:

- **No strike price provided**  
  Returns quotes for about 60 strikes around spot, 30 on each side.
- **Specific strike price provided**  
  Returns quote details for exactly one strike.

It returns at least these fields for each option:
- LTP
- Best Bid
- Best Offer
- Total Buy Qty
- Total Sell Qty
- OI

#### `margin_calculator`
Can accept one or more legs of a strategy and returns the **span margin** required.

### 2.2 User inputs

The engine should ask only these by default:

- `target_pop`  
  Example: 70%, 75%, 80%

- `margin_to_deploy`
  The total capital user wants to allocate.

- `max_loss_appetite`
  The maximum loss the user is willing to tolerate for the strategy as a whole.

Optional:
- `range_outlook`
  Example: “slightly bullish”, “bearish”, “neutral”, or a strike range like `spot -2% to +1%`

### 2.3 Engine philosophy

The engine should be simple for users, but internally it can be smart. Therefore:

- Use **cheap, fast filters first**
- Use **exact margin calculation only for shortlisted candidates**
- Avoid brute forcing all theoretical combinations
- Prefer **structured candidate templates** for each strategy

## 4) Build the Liquid Universe First

The engine should not consider every strike equally. First build a liquid universe.

### 4.1 Step 1: fetch strikes

Use `scrip_master` to get all available strikes for the `scrip + expiry`.

### 4.2 Step 2: enrich quotes

Use `get_option_chain_quotes` to fetch quotes around spot and then, only when needed, fetch missing strikes individually.

### 4.3 Step 3: liquidity screen

A strike is considered liquid for a given option type if:

- `Total Buy Qty > 0`
- `Total Sell Qty > 0`

You may optionally add soft filters:

- `OI > 0`
- `Bid > 0`
- `Ask > 0`
- `Bid-Ask spread` not too wide
- `LTP` not stale
- `OI` above a minimum percentile of the universe

### 4.4 Liquidity tiers

To keep the candidate generation efficient, classify strikes into tiers:

- **Tier A**: high liquidity, tight spread, near spot
- **Tier B**: liquid but moderately farther from spot
- **Tier C**: liquid but only for tail legs or long wings

Suggested scoring for liquidity tier:

```text
liquidity_score =
    w1 * normalized(OI)
  + w2 * normalized(min(total_buy_qty, total_sell_qty))
  + w3 * normalized(1 / spread)
```

Keep only strikes above a configurable threshold for multi-leg candidate generation.

## 5) Strategy Search Design Principles

The engine should not brute-force all combinations of 200+ strikes.

### 5.1 Use strategy templates

Every strategy should be generated by a **template** with structural rules.

Example:
- Short straddle = one ATM CE sell + one ATM PE sell
- Iron condor = one OTM call credit spread + one OTM put credit spread
- Bull call spread = lower strike call buy + higher strike call sell

### 5.2 Use anchor strikes

Build candidate sets around a small set of anchor strikes:

- ATM strike
- 1-step ITM / OTM
- 2-step ITM / OTM
- 3-step ITM / OTM
- Liquidity peaks around spot

This avoids evaluating all combinations.

### 5.3 Use pre-filtered strike windows

For each strategy, define a narrow strike window based on:

- Spot price
- User outlook
- Target PoP
- Expected premium decay zone
- Liquidity tier

Example:
- Short straddle: around ATM ± 1 strike
- Iron condor: wings typically 1 to 5 strikes away from ATM, then filtered by premium and PoP
- Long strangle: further OTM than short strangle
- Butterfly/condor: symmetric or near-symmetric around ATM, unless asymmetry improves margin or PoP

### 5.4 Use economic pruning before margin calculation

For each candidate:

1. Estimate net premium
2. Estimate payoff band and max loss
3. Estimate PoP
4. Reject candidates that obviously fail user constraints
5. Only then call `margin_calculator`

This is the main way to stay fast.

## 6) Strike Selection Heuristics

### 6.1 Common anchor logic

Define:

- `spot`
- `atm_strike = nearest strike to spot`
- `step = strike increment`
- `candidate_calls = strikes above ATM`
- `candidate_puts = strikes below ATM`

A strike can be described as:
- `ATM`
- `OTM1`, `OTM2`, `OTM3`, ...
- `ITM1`, `ITM2`, `ITM3`, ...

### 6.2 Recommended candidate windows

These are starting windows; the engine should adjust them based on liquidity and user target PoP.

- **Short premium strategies**: `ATM ± 1 to 5 steps`
- **Long premium strategies**: `ATM ± 1 to 8 steps`
- **Defined-risk spreads**: `ATM ± 1 to 6 steps`
- **Condors / butterflies**: usually `1 to 5 steps` away on each side

### 6.3 Preferred strike ordering

For credit strategies:
- Prefer higher premium near spot
- Prefer tight spread
- Prefer high OI / high activity
- Prefer strikes that keep max loss within appetite

For debit strategies:
- Prefer lower premium debit if the user is capital constrained
- Prefer strikes with sufficient movement room
- Prefer liquidity in both legs

### 6.4 Asymmetric strikes are allowed

The engine should support asymmetric structures if they improve the score.

Examples:
- Asymmetric iron condor
- Unequal butterfly wings
- Unequal condor widths

This is especially useful when:
- Liquidity is uneven
- Margin efficiency is better
- The user’s outlook is skewed bullish or bearish

## 7) General Sizing Logic

The engine must size strategies by both:

1. **Margin availability**
2. **Max loss appetite**

### 7.1 Total margin

For a strategy with `n` lots per leg, compute:

```text
required_span_margin = margin_calculator(strategy_legs_with_one_lot)
elm = if user_provisions_for_it:
          total_qty_across_all_legs * spot * 2%
      else:
          0
total_margin_per_lot = required_span_margin + elm_per_lot
```

For multi-lot sizing:

```text
total_margin_for_qty = qty_multiplier * total_margin_per_lot
```

### 7.2 Max loss per lot

Max loss depends on strategy type.

Generic formula:

```text
max_loss_per_lot = worst_case_strategy_loss
```

Then:

```text
qty_by_loss = floor(max_loss_appetite / max_loss_per_lot)
qty_by_margin = floor(margin_to_deploy / total_margin_per_lot)
final_qty = min(qty_by_loss, qty_by_margin)
```

### 7.3 Quantity allocation across legs

All legs in a strategy should scale by the same quantity multiplier to preserve ratio.

Examples:
- 1x1 spread
- 1x1x1x1 condor
- 1x2x1 butterfly

### 7.4 Handling infinite-loss strategies

For naked shorts and other theoretically uncapped-loss strategies:

- The engine may ignore `max_loss_appetite` as a hard filter, as requested
- But it should still:
  - show a warning
  - require margin availability
  - cap quantity by margin
  - optionally cap by a policy limit if your app wants to be safer later

---

## 8) PoP Estimation Framework

The engine should use a simple but defensible PoP estimate.

### 8.1 Priority order

1. If IV / Greeks are available, use a proper probability model.
2. If IV is not available, use a premium-and-moneyness heuristic.
3. For final ranking, use a normalized PoP score rather than a false sense of precision.

### 8.2 Practical PoP approximation

For credit structures, estimate the probability of profit as:

```text
PoP ≈ probability that spot finishes inside profitable zone at expiry
```

For a short option or spread, this profitable zone is bounded by breakevens.

A simple fallback approximation:

- Wide away-from-spot strikes => higher PoP
- Higher credit relative to width => higher PoP only up to a point
- Shorter-dated options => faster theta decay, but usually tighter room for error

### 8.3 Normalized PoP score

Define:

```text
pop_score = 1 - normalized(distance_of_breakeven_from_spot)
```

Or if using distribution-based logic:

```text
pop_score = N(d2) for the relevant expiry boundary
```

The exact method can be swapped later without changing the strategy templates.

# 9A) Income Strategies

Income strategies generally benefit from:
- high liquidity
- high credit
- wider probability of profit
- controlled width when defined-risk

---

## 9A.1 Naked Call Short (`naked_ce_short`)

### Structure
- Sell 1 CE

### Strike selection
- Prefer OTM call strikes with good liquidity
- Usually 1 to 5 steps above ATM
- Use user’s bullish/neutral outlook if provided; otherwise rank by credit, liquidity, and PoP

### Candidate generation
1. Collect liquid calls above ATM
2. Keep a strike window around ATM + nearby OTM strikes
3. Rank by:
   - premium collected
   - liquidity
   - PoP proxy
   - margin efficiency

### Sizing
- Quantity = minimum of:
  - `margin_to_deploy / margin_per_lot`
  - any internal policy cap
- Ignore max loss appetite if configured to do so

### Notes
- Highest risk of the income set
- Show clear warning in UI

---

## 9A.2 Naked Put Short (`naked_pe_short`)

### Structure
- Sell 1 PE

### Strike selection
- Prefer OTM put strikes with good liquidity
- Usually 1 to 5 steps below ATM

### Candidate generation
1. Collect liquid puts below ATM
2. Rank lower strikes by:
   - premium
   - liquidity
   - PoP
   - margin efficiency

### Sizing
- Same logic as naked call short

### Notes
- Strongest fit in mildly bullish to neutral markets

---

## 9A.3 Short Straddle (`short_straddle`)

### Structure
- Sell 1 ATM CE
- Sell 1 ATM PE

### Strike selection
- Use the ATM strike
- If exact ATM is illiquid, use nearest liquid strike pair around ATM
- Prefer the strike where both CE and PE are liquid

### Candidate generation
1. Start from ATM
2. Look at ATM ± 1 step only if the exact ATM pair is weak
3. Keep only pairs where both legs pass liquidity criteria

### Ranking
- Highest credit at or near ATM
- Tight bid-ask spread
- High OI
- Reasonable margin usage

### Sizing
- Final qty by margin
- Max loss can be ignored or used as a warning only if configured that way

### Notes
- Best when user is strongly neutral and expects range-bound movement
- High gamma risk near expiry

---

## 9A.4 Short Strangle (`short_strangle`)

### Structure
- Sell 1 OTM CE
- Sell 1 OTM PE

### Strike selection
- Choose OTM call and OTM put with enough premium and liquidity
- Use symmetric or near-symmetric distance from spot when possible
- If asymmetry helps match user outlook, allow it

### Candidate generation
1. Create a call set above ATM
2. Create a put set below ATM
3. Pair strikes where:
   - both are liquid
   - combined credit is acceptable
   - distance from spot satisfies target PoP
4. Avoid full Cartesian product:
   - only compare a limited band of OTM calls and OTM puts
   - pair strikes with similar distance buckets first

### Efficient pairing rule
Instead of all call-put combinations, use:
- same distance bucket
- one-step skew bucket
- two-step skew bucket

For example:
- CE OTM2 with PE OTM2
- CE OTM3 with PE OTM3
- CE OTM2 with PE OTM3
- CE OTM3 with PE OTM2

### Sizing
- By margin
- Ignore max loss if configured to do so

---

## 9A.5 Iron Condor (`iron_condor`)

### Structure
- Sell 1 OTM PE
- Buy 1 lower-strike PE
- Sell 1 OTM CE
- Buy 1 higher-strike CE

### Strike selection
This is the first strategy where brute force becomes expensive. Use a constrained search.

#### Step 1: choose short strikes
- Build a shortlist of liquid OTM puts and calls around spot
- Prefer symmetric short strikes around ATM
- Prefer strikes with enough premium to justify width

#### Step 2: choose wing strikes
- For each short put, pick a farther OTM put as the long wing
- For each short call, pick a farther OTM call as the long wing
- Wing widths should be small enough to keep margin efficient but large enough to meet PoP and credit goals

### Candidate pruning
Do not evaluate every possible 4-leg combination.

Instead:
1. Select top `K` short puts by score
2. Select top `K` short calls by score
3. For each short put, only consider `M` wing puts below it
4. For each short call, only consider `M` wing calls above it

Typical values:
- `K = 5 to 10`
- `M = 2 to 4`

This reduces combinations from thousands to tens.

### Additional pruning rules
Keep only condors that satisfy:
- both short legs are liquid
- both long wings are liquid
- credit is non-trivial
- width is not absurdly wide
- total margin fits deployable capital
- estimated PoP meets user target

### Ranking
Primary ranking factors:
- higher PoP
- better credit-to-margin efficiency
- tighter and balanced structure
- stronger liquidity

### Sizing
- Max loss per lot is approximately:
  - `max(width_put, width_call) - net_credit`
  - for symmetric condors, width is often equal on both sides
- Final qty by:
  - margin
  - max loss appetite

### Notes
- One of the best risk-defined income structures
- Good default for a simple user-facing engine

---

## 9A.6 Iron Butterfly (`iron_butterfly`)

### Structure
- Sell 1 ATM CE
- Sell 1 ATM PE
- Buy 1 OTM CE
- Buy 1 OTM PE

### Strike selection
- Use the ATM short straddle as the anchor
- Select wings at equal or near-equal distances from ATM
- Allow asymmetry if one side is illiquid or expensive

### Candidate generation
1. Find the best ATM pair
2. Choose wing distances from 1 to 4 strikes away
3. Build only a small number of wing combinations

### Ranking
- Higher credit is attractive
- Balanced wings preferred
- Must satisfy target PoP and margin constraints

### Sizing
- Max loss per lot is approximately:
  - `wing_width - net_credit`
- Quantity by minimum of loss and margin capacity

### Notes
- Very strong for range-bound views
- Usually more capital efficient than a wide condor, but tighter risk zone

---

## 9A.7 Bull Put Spread (`bull_put_spread`)

### Structure
- Sell 1 higher-strike PE
- Buy 1 lower-strike PE

### Strike selection
- Prefer OTM puts below spot
- Short strike closer to ATM
- Long strike farther OTM

### Candidate generation
1. Short put shortlist: liquid, higher premium, close enough to spot
2. For each short put, choose a farther OTM long put
3. Limit widths to a small set of steps

### Ranking
- Better credit
- Higher PoP
- Smaller width for capital efficiency
- Good liquidity

### Sizing
- Max loss per lot:
  - `spread_width - net_credit`
- Quantity by loss and margin

### Notes
- Excellent bullish-to-neutral income spread

---

## 9A.8 Bear Call Spread (`bear_call_spread`)

### Structure
- Sell 1 lower-strike CE
- Buy 1 higher-strike CE

### Strike selection
- Prefer OTM calls above spot
- Short call closer to ATM, long call farther OTM

### Candidate generation
Same template logic as bull put spread, but on calls.

### Ranking
- Better credit
- Higher PoP
- Tighter spread and good liquidity

### Sizing
- Max loss per lot:
  - `spread_width - net_credit`

### Notes
- Good bearish-to-neutral income spread

---

# 9B) Directional Strategies

Directional strategies should be used when the user has a clearer bullish or bearish view.

---

## 9B.1 Bull Call Spread (`bull_call_spread`)

### Structure
- Buy 1 lower-strike CE
- Sell 1 higher-strike CE

### Strike selection
- Choose a liquid call near ATM for the long leg
- Choose a farther OTM call for the short leg
- Prefer spreads that cost less while preserving enough upside

### Candidate generation
1. Long call shortlist around ATM to slightly ITM
2. For each long call, choose a short call above it
3. Keep a small set of widths

### Ranking
- Lower debit
- Better upside/risk ratio
- Strong liquidity
- If user has bullish outlook, favor delta-aligned structures

### Sizing
- Max loss per lot = net debit
- Quantity by:
  - `floor(max_loss_appetite / net_debit)` if max loss is enforced
  - `floor(margin_to_deploy / total_margin_per_lot)` if margin is the binding constraint

### Notes
- A clean bullish defined-risk position

---

## 9B.2 Bear Put Spread (`bear_put_spread`)

### Structure
- Buy 1 higher-strike PE
- Sell 1 lower-strike PE

### Strike selection
- Choose a liquid put near ATM for the long leg
- Choose a farther OTM put for the short leg

### Candidate generation
Same as bull call spread, but mirrored for puts.

### Ranking
- Lower debit
- Better downside capture
- Liquidity and width efficiency

### Sizing
- Max loss = net debit

---

## 9B.3 Long Call (`long_call`)

### Structure
- Buy 1 CE

### Strike selection
- Prefer ATM or slightly ITM for better delta
- If user wants cheaper convexity, allow OTM call strikes
- Liquidity is critical because exit quality matters

### Candidate generation
1. Build a shortlist of liquid calls from ITM to OTM
2. Score by:
   - moneyness
   - premium affordability
   - liquidity
   - exposure to expected move

### Ranking
- Lower debit
- Strong directional alignment
- Better liquidity
- Higher user target PoP if buying closer to ATM

### Sizing
- Max loss per lot = premium paid
- Qty = minimum of loss-cap and margin-cap

---

## 9B.4 Long Put (`long_put`)

### Structure
- Buy 1 PE

### Strike selection
- Prefer ATM or slightly ITM
- Cheap OTM puts can be considered only if user explicitly wants convex downside exposure

### Ranking and sizing
Same as long call.

---

# 9C) Volatility Strategies

Volatility strategies are best when the user expects a large move but is unsure of direction, or expects dispersion around the spot.

---

## 9C.1 Long Straddle (`long_straddle`)

### Structure
- Buy 1 ATM CE
- Buy 1 ATM PE

### Strike selection
- Use ATM pair
- If exact ATM illiquid, use the nearest liquid pair

### Candidate generation
- Small search around ATM only
- Focus on liquidity and total debit

### Ranking
- Lower total debit
- Strong liquidity
- Better expected move capture
- Acceptable breakeven distance

### Sizing
- Max loss per lot = total debit
- Qty by margin and loss appetite

### Notes
- Pure volatility expression
- Needs a meaningful move to profit

---

## 9C.2 Long Strangle (`long_strangle`)

### Structure
- Buy 1 OTM CE
- Buy 1 OTM PE

### Strike selection
- Use symmetric or near-symmetric OTM strikes
- Choose closer strikes for lower debit, farther strikes for lower probability but larger move leverage

### Candidate generation
1. Build OTM call set
2. Build OTM put set
3. Pair them using distance buckets, not full Cartesian search

### Ranking
- Lower debit
- Adequate expected move
- Liquidity
- Better PoP if strikes are not too far OTM

### Sizing
- Max loss = total debit

---

## 9C.3 Long Butterfly (`long_butterfly`)

### Structure
Common call butterfly example:
- Buy 1 lower-strike CE
- Sell 2 middle-strike CE
- Buy 1 higher-strike CE

A put butterfly can be built similarly. The engine may support both, or choose the cheaper side.

### Strike selection
- The middle strike is typically ATM or near ATM
- Wings should be equidistant by default
- Allow asymmetry if it improves liquidity or cost

### Candidate generation
1. Pick a middle strike near ATM
2. Choose wing distances from a small set of values
3. Build only a small number of butterflies around the anchor

### Ranking
- Lower net debit
- Strong pinning potential around the middle strike
- Liquidity across all three strikes
- Better defined payoff fit

### Sizing
- Max loss = net debit
- Quantity by margin and max loss

### Notes
- Good when user expects price to settle near a specific zone

---

## 9C.4 Long Condor (`long_condor`)

### Structure
Typical call condor:
- Buy 1 lower-strike CE
- Sell 1 second lower-strike CE
- Sell 1 second higher-strike CE
- Buy 1 higher-strike CE

Or the put version, depending on pricing and liquidity.

### Strike selection
- Use a structured four-strike ladder
- Prefer evenly spaced strikes
- Allow asymmetry for better pricing

### Candidate generation
1. Build candidate strike ladders from liquid strikes
2. Use distance buckets rather than brute-force enumeration
3. Keep only ladders with reasonable debit and sensible wings

### Ranking
- Lower debit
- Better liquidity
- Better range capture
- Good balance between payoff width and cost

### Sizing
- Max loss = net debit
- Quantity by loss and margin

## 10) Optimal Combination Search Logic

This is the key part that prevents brute force over 200+ strikes.

### 10.1 General candidate search algorithm

For each strategy:

1. Identify the anchor strike(s)
2. Build a narrow strike window around the anchor
3. Filter by liquidity
4. Bucket strikes by distance from spot
5. Form combinations only inside those buckets
6. Score cheaply
7. Keep top `N`
8. Call `margin_calculator` only for the top set
9. Re-rank using exact margin and exact max loss

### 10.2 Bucket-based pairing

Use distance buckets from ATM:

- `bucket 1`: 1 strike away
- `bucket 2`: 2 strikes away
- `bucket 3`: 3 strikes away
- `bucket 4`: 4 strikes away

For a condor:
- short legs may come from bucket 1 to 3
- long wings may come from bucket 2 to 5

This turns a combinatorial problem into a manageable set of structured pairs.

### 10.3 Symmetry preference

For range strategies:
- Prefer symmetric structures first
- Then relaxed symmetric
- Then asymmetric only if it improves the score

### 10.4 Early discard rules

Reject candidates if any of these is true:

- one or more legs are illiquid
- credit/debit is too small to matter
- width is too large for the user’s capital
- estimated max loss exceeds appetite
- PoP is below target by a meaningful margin
- the spread between bid and offer is too wide
- expected fill quality is poor

### 10.5 Shortlist size

Recommended shortlist sizes:
- 5–10 short strikes
- 2–4 wing strikes per side
- 10–30 final candidates per strategy before exact margin calculation

This is usually enough to avoid brute force while still finding good trades.

## 11) Quantities and Risk Sizing

### 11.1 Basic quantity formula

For each candidate:

```text
qty_by_margin = floor(margin_to_deploy / total_margin_per_lot)
qty_by_loss = floor(max_loss_appetite / max_loss_per_lot)
final_qty = min(qty_by_margin, qty_by_loss)
```

### 11.2 Margin-aware total lot sizing

When `margin_calculator` returns a span margin for one lot-equivalent of the strategy:

```text
span_margin_total = span_margin_per_lot * final_qty
```

If provisioning ELM:

```text
elm_total = final_qty * total_legs_qty * spot * 0.02
```

Then:

```text
total_required_capital = span_margin_total + elm_total
```

### 11.3 Lot size conversion

If your exchange contract lot size is `lot_size`, then:

```text
contracts = final_qty * lot_size
```

Make sure max loss and margin calculations are consistent in the same unit system.

### 11.4 Width-based max loss for defined-risk structures

For a vertical spread:

```text
max_loss_per_lot = spread_width - net_credit
```

For a butterfly or condor, use the worst-case payoff region.

For a debit strategy:

```text
max_loss_per_lot = net_debit
```

For naked shorts:
- max loss is theoretically uncapped
- do not apply a strict max-loss gate if user settings allow it

## 12) Ranking Framework

After generating feasible candidates, rank them.

### 12.1 Suggested score components

- `PoP score`
- `Margin efficiency`
- `Risk score`
- `Liquidity score`
- `Credit/debit attractiveness`
- `Directional alignment score` if user provided an outlook
- `Width quality score`
- `Fill quality score`

### 12.2 Example composite score

```text
final_score =
    0.30 * pop_score
  + 0.20 * liquidity_score
  + 0.20 * margin_efficiency_score
  + 0.15 * risk_fit_score
  + 0.10 * premium_score
  + 0.05 * outlook_alignment_score
```

You can tune weights by strategy family:

- Income strategies: emphasize PoP and credit
- Directional strategies: emphasize move capture and debit efficiency
- Volatility strategies: emphasize debit and expected-move suitability

### 12.3 Family-specific ranking

#### Income
Prefer:
- better PoP
- higher credit
- narrower but not too narrow widths
- stable liquidity

#### Directional
Prefer:
- lower debit
- stronger delta alignment
- manageable max loss

#### Volatility
Prefer:
- low debit
- better breakout potential
- liquidity at all legs

## 13) Suggested Execution Flow

### 13.1 High-level flow

1. Load strikes from `scrip_master`
2. Fetch option quotes around spot
3. Build liquid universe
4. Identify ATM and strike buckets
5. For each requested strategy:
   - generate structured candidates
   - apply cheap filters
   - shortlist top candidates
   - call `margin_calculator`
   - compute ELM if applicable
   - size quantity
   - rank and return top results
6. Present only the best few trades

### 13.2 Suggested output to user

For each top candidate show:

- Strategy name
- Legs
- Strike levels
- Net credit/debit
- Span margin
- ELM
- Total required capital
- Max loss
- Breakevens
- Estimated PoP
- Quantity
- Why it was chosen

## 14) Pseudocode

```python
def build_engine(scrip, expiry, user_inputs):
    all_strikes = get_scrip_master_strikes(scrip, expiry)
    spot = get_spot_price(scrip)
    option_chain = get_option_chain_quotes(scrip, expiry)

    liquid_universe = []
    for opt in option_chain:
        if opt.total_buy_qty > 0 and opt.total_sell_qty > 0:
            liquid_universe.append(opt)

    atm = nearest_strike(spot, all_strikes)
    strike_buckets = build_strike_buckets(all_strikes, atm)

    results = []
    for strategy_name in requested_strategies(user_inputs):
        candidate_templates = generate_candidates(
            strategy_name,
            liquid_universe,
            strike_buckets,
            spot,
            user_inputs
        )

        cheap_filtered = []
        for c in candidate_templates:
            c.estimated_pop = estimate_pop(c, spot, user_inputs)
            c.estimated_loss = estimate_max_loss(c)
            c.estimated_credit_or_debit = estimate_premium(c)

            if not passes_basic_filters(c, user_inputs):
                continue
            cheap_filtered.append(c)

        shortlist = top_n(cheap_filtered, key=heuristic_score, n=20)

        for c in shortlist:
            c.span_margin = margin_calculator(c.legs)
            c.elm = calculate_elm(c, spot, user_inputs)
            c.total_margin = c.span_margin + c.elm

            c.final_qty = size_quantity(c, user_inputs)
            if c.final_qty <= 0:
                continue

            c.max_loss_total = c.estimated_loss * c.final_qty
            c.total_margin_total = c.total_margin * c.final_qty

            if c.total_margin_total > user_inputs.margin_to_deploy:
                continue
            if is_defined_risk(c) and c.max_loss_total > user_inputs.max_loss_appetite:
                continue

            c.final_score = final_ranking_score(c, user_inputs)
            results.append(c)

    return top_results(results)
```

## 16) Edge Cases and Guardrails

### 16.1 Missing quote data
If a leg is missing a quote:
- do not use it unless the engine can fetch it directly
- prefer a fully quoted strategy

### 16.2 Wide bid-ask spread
Reject or down-rank strikes with poor execution quality.

### 16.3 Uneven liquidity
Allow asymmetry only when it clearly improves the candidate.

### 16.4 Near-expiry options
Tighten liquidity and fill-quality requirements.

### 16.5 Huge user margin with small max loss
Use the stricter of the two constraints, unless strategy is uncapped and user has explicitly allowed it.

### 16.6 Infinite-loss strategies
Show a warning badge and avoid presenting them as safe.

## 17) Recommended Product Behavior

To keep the UI simple:

### Ask the user only:
- Target PoP
- Margin to deploy
- Max loss appetite

### Ask range outlook only when:
- a directional strategy is being optimized
- or when the user wants the engine to prioritize one side of the market

### Return:
- one best trade per strategy family
- plus an overall best trade if the user wants only one recommendation

## 18) Design Choice Summary

This engine should work well because it:

- uses liquid-universe filtering first
- avoids brute force through template-driven generation
- uses bucket-based strike pairing
- ranks cheap before calling exact margin APIs
- sizes by both margin and max loss
- supports symmetric and asymmetric structures
- keeps the user experience simple

## 20) Final Note

The key to making this engine scale is not more exhaustive searching. It is:
- **good anchoring**
- **strict liquidity filtering**
- **strategy-specific candidate templates**
- **early pruning**
- **margin-aware ranking**

That is what lets the engine handle 200+ strikes without exploding the search space.
